# Rust-Portierung – TASK-0126

Die Portierung wird auf `port/task-0126-rust` umgesetzt. Referenz ist der unveränderte TypeScript-/Vue-Stand `b40b2dde246533a25a18148a6b59faced676d9ba`. Der native Code liegt unter `native/src`, mit `Cargo.toml`, gepinntem Toolchainstand und `Cargo.lock` im Repositorywurzelverzeichnis.

Der aktuelle Zwischenstand enthält einen nativen HTTP-/MCP-Daemon und eine CLI mit stdio-Bridge und eingebetteter vorhandener Vue-Oberfläche. Persistenz, Secrets, Autorisierung, Core, geteilte Medien, Simulator sowie HID-/Bildadapter für PiKVM, beide Comet-Modelle und JetKVM sind integriert. Alle sechs Computer-Tools verwenden über REST, Streamable HTTP und stdio dieselben nativen Sessions, Leases, Gerätequeues und Request-Journale. Der vollständige Funktionsumfang bleibt beim vorhandenen TypeScript-Daemon: Janus/Audio einschließlich JetKVM-Opus sowie die Pluginruntime sind noch offen. Der native Zwischenstand ersetzt noch keine bestehende Installation; die Gesamtabnahme bleibt offen.

## Bauen und prüfen

Rust `1.99.1` mit MSVC-Buildwerkzeugen auf Windows; auf Linux/macOS jeweils eine passende native C-Toolchain. SQLite und der WebRTC-Cryptoprovider AWS-LC werden statisch gebaut; dessen Build benötigt zusätzlich CMake (unter Windows die vom Crate verwendeten NASM-Artefakte). Ein separater OpenSSL-Laufzeitdienst ist nicht erforderlich. Abhängigkeiten sind im Lockfile gebunden. Die Bibliothek und ihre regulären Tests können ohne Node/npm und ohne vorgebauten Webbundle gebaut werden:

```sh
cargo build --locked
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
```

Die regulären Cargo-Tests benötigen kein Node/npm. Neun zusätzliche Vergleiche führen bewusst den bestehenden TypeScript-Code aus; dafür zuerst dessen Bundle bauen:

```sh
npm ci
npm run build
cargo test --locked --test legacy_compat -- --ignored
```

Das ausführbare Binary verlangt das Feature `embedded-web` und einen vorhandenen Produktionsbundle unter `dist/web`; bei fehlendem `index.html` bricht der Build ab. Der Rust-Build ruft Node nicht selbst auf und bindet nur reguläre Dateien aus diesem Verzeichnis ein. Symlinks werden abgewiesen. Nach Änderungen an der Oberfläche zuerst erneut `npm run build` ausführen und danach das Binary neu bauen:

```sh
npm ci
npm run build
cargo build --locked --release --features embedded-web
cargo clippy --locked --all-targets --features embedded-web -- -D warnings
cargo test --locked --features embedded-web
```

Für eine isolierte Vorschau mit ausschließlich simulierten Geräten, im Repositoryverzeichnis (unter Windows hat das Binary die Endung `.exe`):

```sh
target/release/kvmhelm token bootstrap --data .kvmhelm/native-preview/data --secrets .kvmhelm/native-preview/secrets
target/release/kvmhelm demo --data .kvmhelm/native-preview/data --secrets .kvmhelm/native-preview/secrets
target/release/kvmhelm serve --host 127.0.0.1 --port 8765 --data .kvmhelm/native-preview/data --secrets .kvmhelm/native-preview/secrets
```

Den PAT aus `.kvmhelm/native-preview/secrets/cli.pat` im Browserlogin eingeben. Ohne den ausdrücklichen `demo`-Aufruf bleibt eine neue Installation leer. Nach dem Build benötigt dieser native HTTP-/Simulator-/KVMD-Pfad weder Node/npm noch `dist/web` am Laufzeitort. JetKVM-HID und Video laufen nativ mit explizitem FFmpeg-Helfer; vollständige Audio- und Plugininstallationen benötigen weiterhin den TypeScript-Daemon.

Die native CLI unterstützt `serve`, `demo`, `token bootstrap/create/list/revoke`, `device list/add/test/benchmark/stop/resume`, `mcp --transport stdio`, `doctor` und `secrets cleanup`. Remoteverwaltung spricht den laufenden Daemon an; sie öffnet keinen zweiten Core. `device add --file` liest wie die bisherige CLI ein Objekt mit `device` sowie optional `secret` und `ca`. `token create --out` und Bootstrap legen ausschließlich neue private Dateien an und prüfen deren Verfügbarkeit vor der Tokenausgabe. Mit `--out` wird der PAT nicht auf stdout ausgegeben; ohne diese Option liefert `token create` wie bisher den einmaligen Token zurück. Bootstrap und Secretbereinigung sind weiterhin Offlineoperationen.

Die bestehenden `KVMHELM_DATA`, `KVMHELM_SECRETS`, `KVMHELM_URL`, `KVMHELM_PAT`, Listener-/TLS- sowie Session-/Replay-Umgebungsoptionen werden unterstützt. `--pat-file` wählt die geschützte PAT-Datei, `--origin` kann für weitere kanonische HTTP(S)-Origins mehrfach angegeben werden. Die native CLI lädt `.env` nicht automatisch; benötigte Variablen müssen exportiert sein. `--lan-host/--lan-port` öffnet einen zweiten TLS-Listener auf demselben Core; `--cert/--key` sind dafür erforderlich. Ein nicht als Loopback erkannter Listener verlangt immer TLS. Ohne `--lan-host` gelten die Zertifikatoptionen für den primären Listener. SIGINT und unter Unix SIGTERM beenden Listener, angenommene Arbeit, Core und Store geordnet; Windows-Prozessbeendigung per Kill ist kein geordneter Dienststopp. Dienstinstallation, Container und Releasepakete werden erst nach der Gesamtintegration umgestellt.

## Persistenz und Kompatibilität

Schema v1 und seine Tabelle `documents(kind,id,json,revision)` bleiben unverändert. Vorhandene Geräte-/Token-/Präferenz-/Plugindokumente werden mit der gespeicherten Revision gelesen. Eine Schreiboperation verwendet eine `BEGIN IMMEDIATE`-Transaktion mit Revisionsvergleich; Konflikte führen zu `REVISION_CONFLICT`. Überfüllung der Queue führt vor Annahme zu `RESOURCE_LIMIT`. Ein Antwort-Timeout schließt weitere Zugriffe dieses Storehandles; ein möglicherweise bereits erfolgter Commit wird nicht automatisch wiederholt.

Der Masterkey bleibt die vorhandene 32-Byte-Datei `master.key`. Ein Secret enthält weiterhin zwölf IV-Bytes, 16 GCM-Tag-Bytes und danach den Chiffretext des UTF-8-JSON. `secret_ref` und `tls.ca_ref` bleiben Dateireferenzen. Der neue Baustein ersetzt defekte oder falsch lange Masterkeys nicht. Secret- und Masterkey-Dateien werden privat angelegt; Windows erhält eine geschützte DACL für den ausführenden Benutzer mit entsprechender Vererbung am gewählten Verzeichnis, POSIX verwendet 0700/0600. Vorhandene gewählte Daten-/Secretverzeichnisse und gelesene Secretdateien werden ebenfalls auf diesen Benutzer beschränkt. Ein Dienst muss unter dem zur Installation passenden Konto laufen. NTFS-ACLs wurden lokal geprüft; andere Windows-Dateisysteme und entfernte Freigaben sind nicht abgenommen.

Secretdateien sind auf 1 MiB einschließlich IV/Tag begrenzt; die bestehenden Gerätecredentials und maximal 64-KiB-CA-Eingaben passen darin. Offlinebereinigung löscht nur erkannte, nicht referenzierte, mindestens einen Tag alte generierte Secretdateien. Neue, referenzierte, fremd benannte Dateien und Links bleiben erhalten.

Schema v0 mit vorhandenen Tabellen erhält vor der Übernahme ein privates `config.sqlite.pre-v1-<UUID>.bak` über die SQLite-Backup-API. Unbekannte neuere Schemata werden vor Formatänderungen abgewiesen. Ein explizites Backup überschreibt keine vorhandene Datei und enthält committed WAL-Daten. Backup und Restore für einen späteren Betriebswechsel weiterhin bei gestopptem Daemon durchführen: Datenverzeichnis und separat geschützt das Secretverzeichnis samt Masterkey sichern; Restore in eine separate Kopie mit demselben Format, dann prüfen. Medien, Live-Sessions und Leases werden nicht persistiert. Eine native Migrations-CLI ist noch nicht vorhanden.

Die strikten Eingabeverträge verwenden `Validate::parse` an JSON-Grenzen. Das berücksichtigt insbesondere Objektformen (Serde akzeptiert sonst teils Arrays als Structs), Ablehnung unbekannter Felder, `optional` gegenüber `null`, Zod-Defaults, sichere Ganzzahlen einschließlich JSON `1.0` sowie die Unicode-Codepoint-Längen des gepinnten Zod 4.5. Einzelne ungültige UTF-16-Surrogate in JSON werden vom Rust-JSON-Parser abgewiesen; gewöhnlicher Unicode einschließlich Emoji bleibt erhalten. Die finale API-Abnahme muss auch diese Parsergrenze ausweisen.

## Core und Medien

`Core` besitzt Gerätezustände, Sessions, Leases, Treiber und Medienquellen. Ein Treibervertrag in `drivers/mod.rs` stellt Verbindung, Capabilities, vollständige Vorprüfung, Eingaben, Freigabe, Snapshots und optionalen Videostream bereit. Regulär registriert sind `simulator`, `pikvm-v4` und `glinet-comet`. Tests registrieren zusätzlich isolierte Treiber, deren blockierende oder fehlschlagende Operationen gezielt gesteuert werden. Netzwerkadapter werden separat gegen lokale HTTP-/TLS-/WebSocket-Gegenstellen geprüft. Ein Integrationstest verwendet den regulär registrierten PiKVM-Adapter aus dem nativen Core und prüft eine Eingabe samt Retry ohne zweiten HID-Versand.

Jedes Gerät hat eine FIFO mit höchstens 64 angenommenen Eingabeaufträgen einschließlich des laufenden Auftrags. Abbruch des HTTP-/Toolaufrufers beendet einen angenommenen Auftrag nicht und gibt dessen Queueplatz nicht vorzeitig frei. Gleiche Request-ID und gleicher normalisierter Inhalt warten auf dasselbe Ergebnis; anderer Inhalt wird abgewiesen. Eine gesonderte Freigabebarriere erreicht die Queue auch bei vollem Eingabebudget. Not-Stopp widerruft die Generation und bricht einen laufenden Treibervorgang ab, bevor auf die Queue gewartet wird. Resume vergibt keine neue Lease. Ein fehlgeschlagener Freigabeversuch sperrt weitere Steuerung bis zur bewussten Wiederaufnahme.

Konfigurationsänderungen besitzen eine eigene begrenzte FIFO mit derselben Annahmesemantik. Ein bereits angenommener Save/Delete beendet Commit, Laufzeitaustausch und berechtigte Secretbereinigung auch dann, wenn sein Aufrufer verschwindet. Ein veralteter Revisionsstand oder eine fremde Secretreferenz führt zu einem Fehler. Nach ungewissem Store-Commit werden neue Secrets vorsichtshalber behalten. Treiber samt Capabilities werden innerhalb eines gemeinsamen Sieben-Sekunden-Verbindungsbudgets aufgebaut; die nachfolgende Fehlerbereinigung hat ein eigenes Fünf-Sekunden-Budget.

Standardgrenzen sind 128 Sessions insgesamt, höchstens 32 je Token einschließlich laufender Eröffnungen, 256 Request-IDs je Session und Eröffnungsjournal sowie insgesamt 1024 Eröffnungsjournale für verschiedene `(Token, Client)`-Paare. Die neue Begrenzung der Journalanzahl verhindert unbegrenztes Wachstum durch wechselnde Client-IDs. Client-Trennung berücksichtigt auch den Token; identische Client-IDs zweier Tokens teilen keine Ergebnisse. Eine Freigabe bei vollem Sessionjournal schließt sicher die Session. Die Replayverwaltung hält standardmäßig 64 MiB Bilddaten. Verdrängung entfernt nur Bildpayloads, behält Metadaten und Ausführungsstatus und setzt `replay_image_evicted`. Wie im Original bleibt das neueste Ergebnis mit höchstens vier begrenzten Bildern auch bei einem kleineren konfigurierten Budget erhalten. Veröffentlichung und Verdrängung sind gegen gleichzeitige Abschlüsse serialisiert.

Alle Aktionen werden vor dem ersten Effekt geprüft. Native Simulatorprüfungen verwenden dabei bereits das vollständige US-/DE-Mapping; das ist strenger als die ursprüngliche einfache Simulatorprüfung. Ein Batch liefert höchstens vier Bilder, erlaubt insgesamt höchstens 25 Sekunden explizite Wartezeit und hat ein Ausführungsbudget von 30 Sekunden einschließlich Abschlussbild. Ein vor Versand auf `unknown` gesetzter Aktionsstatus wird nur nach bekanntem Treiberergebnis auf `sent` oder `acknowledged` geändert. Ein unbekannter Ausgang stoppt folgende Aktionen; Wiederholung derselben ID sendet keine Eingabe erneut. Mindestlatenz ist eine feste Frist ab Ende des letzten Eingabevorgangs und wird durch Beobachtungen oder Replay nicht neu gestartet.

Medien bleiben ausschließlich im RAM als geteilte unveränderliche Bytes. Gleichzeitige Snapshotaufrufe teilen eine Aufnahme mit maximal fünf Sekunden Treiberlaufzeit; der einzelne Beobachter kann früher auslaufen. Ein Verbindungswechsel verwirft späte Ergebnisse der alten Generation. Captures behalten die bei Beginn erfasste Inputrevision; sie werden nach Eingaben nicht umetikettiert. Nachfolgende Beobachtungen warten auf eine neue passende Aufnahme. Frames sind auf 8 MiB und 16 Megapixel begrenzt. Langsame Abonnenten erhalten den jeweils neuesten vollständigen Frame statt einer wachsenden Queue. Aktive/Übersichts-/Hintergrundprofile verwenden 15/5/1 Snapshotaufrufe je Sekunde. Der Benchmark vergleicht fünf Snapshots mit bis zu fünf Streamframes innerhalb von 2,5 Sekunden und wechselt mit 20 Prozent Hysterese.

Ereignisverlauf und Broadcast sind auf je 256 Einträge begrenzt; Instanz-ID und Sequenz ermöglichen SSE-Replay beziehungsweise einen erkennbaren Neustart. Medienmetriken sowie Dispatch- und Schedulerverläufe sind begrenzt. Netzwerkadapter markieren Capabilities-/Disconnect-Ereignisse mit ihrer Verbindungsepoche; Core verwirft verzögerte Ereignisse alter Verbindungen. HTTP-/SSE-/MCP-Transportbudgets sind integriert; Audio-WebSocket-Budgets, Audiofreigabe und Pluginabonnements folgen mit ihren Adaptern. `mcp::pack` liefert bereits echte Bildblöcke, Annotations und deckungsgleiche Metadaten im ersten Textblock und `structuredContent`.

## Native HTTP-Laufzeit

`server.rs` liefert die eingebetteten Assets, `/healthz`, `/readyz` und die vorhandenen Verwaltungs-, Tool-, Frame-, MJPEG- und SSE-Routen auf demselben Core. Login setzt ein HttpOnly-/SameSite=Strict-Cookie, unter TLS zusätzlich Secure; schreibende Cookieaufrufe benötigen Origin und CSRF-Token. Bearerclients behalten die bisherigen gehashten Client-IDs. Host und Origin werden gegen die Listenerkonfiguration geprüft, doppelte sicherheitsrelevante Header werden abgewiesen. Die Antwortheader enthalten CSP, No-Sniff, No-Referrer und No-Store. LAN-Listener ohne Zertifikat/Key werden bereits vor Bind abgewiesen. Zertifikatinspektion führt ausschließlich DNS-, TCP- und TLS-Prüfung aus und sendet kein HTTP und keine Gerätecredentials.

Pro Listener sind höchstens 512 Verbindungen zugelassen; TLS-Handshakes haben fünf Sekunden und HTTP-Header zehn Sekunden Zeit. JSON-Bodies werden begrenzt eingelesen: maximal 256 KiB innerhalb von zehn Sekunden. Authentifizierung erfolgt vor dem Bodylesen, ausgenommen Login. Angenommene API-Arbeit besitzt einen eigenen Task und läuft bei Socketabbruch zu Ende; der Listener wartet beim geordneten Stop auf diese Arbeit. Damit kann ein verlorener HTTP-Aufrufer einen angenommenen Tokenwiderruf nicht zwischen Datenbankcommit und Laufzeitfreigabe abbrechen. Ein Integrationstest blockiert dafür gezielt SQLite, trennt den Client und prüft anschließend gespeicherten Widerruf und freigegebene Lease.

Die reguläre Requestannahme hat 64 Plätze und eine getrennte Sicherheitsannahme 16. Tokenbasierte Medien-/Kontrollfenster haben standardmäßig 12000/2400 Aufrufe je Minute; Stop, Eingabefreigabe und Schließen verwenden die Sicherheitsannahme und werden durch ein erschöpftes reguläres Fenster nicht blockiert. Login ist auf zehn Versuche je IP/Minute, fehlgeschlagene Authentifizierung auf 120 begrenzt; die gemeinsame Fenstertabelle ist auf 8192 Einträge begrenzt. Health und Readiness bleiben unabhängig davon erreichbar; Readiness prüft tatsächlich den Store. Die IP-Fenster verwenden wie im Original einzelne IPv4-Adressen und IPv6-/56-Präfixe; IPv4-mapped IPv6 zählt zur jeweiligen IPv4-Adresse. Die vollständige Audio-/API-/UI-Abnahme bleibt Bestandteil der offenen Gesamtintegration.

MJPEG und SSE verwenden höchstens 512 aktive Streams je Listener und 64 je Token. Jeder Stream besitzt eine eigene Freigabe und einen Monitor, der spätestens nach einer Sekunde bei Tokenwiderruf/-ablauf oder verlorener Session die Verbindung beendet, auch wenn ein langsamer Empfänger keine weiteren Bodydaten abruft. Video hält eine Übersichtsquelle und liefert ausschließlich den neuesten vollständigen Frame; es kopiert Bildbytes nicht pro Abonnent. Disconnect gibt den Verbraucher frei. SSE nutzt den bestehenden Ring mit Instanz-/Sequenzcursor und beendet einen zu weit zurückgefallenen Liveempfänger. Geräte- und Tokenlisten behalten bei laufender Neuanlage dieselbe Einfügereihenfolge wie der TypeScript-Core; nach Neustart gilt wie bisher die Reihenfolge der Storeabfrage, sofern die explizite UI-Reihenfolge nichts anderes vorgibt.

Die Pluginruntime ist noch nicht integriert. Die echten leeren Inventare `/plugins` und `/ui-extensions` liefern bei einer neuen Installation `[]`. Sobald gespeicherte Plugins vorhanden sind, melden beide Routen sowie die noch unvollständige Plugindiagnostik ausdrücklich `UNSUPPORTED_RUNTIME`; konfigurierte Plugins werden nicht als laufend oder als nicht installiert dargestellt. Installations-/Lifecycle-/Panelrouten und Audio-WebSocket werden erst mit ihren nativen Laufzeitadaptern ergänzt. Fehlende API-Routen liefern einen Fehler.

Die Diagnostik zeigt native Corezähler und Betriebssystemwerte des eigenen Prozesses: RSS und private Bytes unter Windows, RSS unter Linux und kumulierte CPU-Zeit unter Windows/Unix. Nicht verfügbare Werte sind `null`, insbesondere RSS unter macOS. Dies ist kein Rust-Heapzähler und keine Messung von Codec-/Plugin-Helfern. Repräsentative Messszenarien samt Vergleich gegen das Original fehlen weiterhin.

## JetKVM-WebRTC, USB-HID und Video

`drivers/jetkvm.rs` verwendet die tatsächlichen JetKVM-Endpunkte `/device/status`, `/device`, `/auth/login-local` und `/webrtc/signaling/client`. Die vorhandenen Cookies werden nach erfolgreichem Login gespeichert und bei Wiederverbindung wiederverwendet. HTTP und Signaling verwenden denselben LAN-/TLS-/CA-/Fingerprint-Transport wie die übrigen Adapter, ohne KVMD-Endpunkte oder Protokollgleichheit zu unterstellen. Alle konfigurierten TLS-Prüfungen finden vor dem Cookie-/Passwortversand auf dem tatsächlichen Socket statt.

`drivers/jet_peer.rs` betreibt [str0m 0.24.1](https://docs.rs/str0m/0.24.1/str0m/) in einer eigenen begrenzten Ereignisschleife. Das Sans-I/O-Modell überlässt sämtliche Netzwerkaufrufe dem Adapter: bis zu 16 UDP-Bindungen für die Signaling-Schnittstelle und die verfügbaren lokalen/LAN-IPv4-Schnittstellen (mit wiederverwendetem 64-KiB-Empfangspuffer je Socket), ausschließlich lokale/LAN-Kandidaten, Prüfung von SDP und Trickle-ICE vor Übergabe sowie zusätzliche Prüfung jeder UDP-Zieladresse und eingehenden Quelle. Es gibt keine öffentlichen STUN-/TURN-Dienste und keine ICE-DNS-/mDNS-Auflösung. Höchstens 256 Kandidaten sind zulässig; Signalingnachrichten sind auf 64 KiB begrenzt. Nicht erreichbare Kandidaten während des Aufbaus verhindern nicht die Suche nach einem brauchbaren Paar. DTLS-Fingerprintprüfung bleibt eingeschaltet; DTLS/SRTP/SCTP laufen im Rust-Prozess mit statischem Cryptoprovider.

Der geordnete `rpc`-Datenkanal erhält höchstens 64 ausstehende/angenommene Aufträge mit zusammen 64 KiB Anwendungsdaten; zusätzlich begrenzt str0m seine SCTP-Sendeannahme auf 64 KiB. Der interne SCTP-Empfang hat ein 1-MiB-Fenster und 256-KiB-Nachrichtenlimit; die Anwendung weist Nachrichten über 64 KiB ab. Annahmeplätze bleiben bei Aufruferabbruch bis zur tatsächlichen Bearbeitung bestehen. Control wird unmittelbar vor Kanalversand erneut geprüft. RPCs enden nach zwei Sekunden ohne Antwort als `EXECUTION_UNKNOWN`; weder neue noch wiederhergestellte Verbindungen senden sie automatisch erneut. Verbindungsfehler, Signaling-Heartbeat, Kanalende und `otherSessionConnected` beenden den Peer. Verbindungsepochen verhindern verspätete Änderungen alter Peers. Geordnetes Trennen, Geräteaustausch und Shutdown schließen Socket, Medien und den eigenen Decoderhelfer.

Die USB-Umsetzung erhält Reportreihenfolge, Modifizierer, sechs gleichzeitige Nichtmodifizierertasten, DE/US-/AltGr-/Tottasten, Mauskoordinaten, Buttons und Scroll. Die gesamte Aktionsfolge wird vor der ersten Eingabe geprüft. Zustände werden vor potenziell ungewissem Versand festgehalten; All-Release sendet leere Tastatur- und buttonfreie Mausreports. Der bestehende öffentliche Aktionsstatus bleibt `sent`, auch wenn JetKVM die RPC-Annahme bestätigt.

`drivers/h264.rs` setzt einzelne NALs, STAP-A und FU-A aus RTP zusammen, berücksichtigt Sequenzüberlauf/Duplikate/Lücken und erhält SPS/PPS über Verluste hinweg. Nur vollständige Access Units bis 8 MiB erreichen den Decoder; höchstens 4096 NALs und zwei Parameterblöcke bis je 64 KiB bleiben gespeichert. Fehlende Marker, widersprüchliche Fragmente und Größenüberschreitungen verlangen eine neue IDR. Nach Verlust oder Decoder-Rückstau werden PLI-Anfragen höchstens alle 500 ms gesendet und Zwischenbilder bis zum nächsten Keyframe verworfen.

H.264-Decodierung und JPEG-Erzeugung verwenden weiterhin einen dauerhaften FFmpeg-Prozess je verbundenem JetKVM. Programmsuche: explizites `KVMHELM_FFMPEG`, danach `ffmpeg[.exe]` neben dem nativen Binary, danach `ffmpeg` im PATH. Ein fehlendes Programm meldet `DEPENDENCY_MISSING`. Es werden nur Pipes, zwei Codec-Threads, maximal ein wartendes Access Unit neben dem gerade geschriebenen und jeweils das neueste JPEG verwendet. Bilddaten werden weder auf Platte geschrieben noch geloggt; stderr des Helfers wird verworfen. Der Input setzt FFmpegs [Pixelgrenze](https://ffmpeg.org/doxygen/8.1/structAVCodecContext.html) auf 16.777.216 und die maximale Einzelallokation auf 64 MiB. Der JPEG-Parser hat zusätzlich Byte-/Pixelgrenzen. Das ist keine Behauptung eines 64-MiB-Gesamtlimits für FFmpeg; sein Arbeitssatz muss in der späteren Prozessbaummessung mitgezählt werden.

Eingehendes Opus wird im SDP weiterhin verhandelt; native Decodierung, PCM-Verteilung und Audio-WebSocket folgen mit dem gemeinsamen Audiopfad. Capabilities melden bis dahin ausdrücklich die fehlende Audiointegration. Eine JetKVM-Mikrofonrichtung wird nicht als vorhanden ausgegeben. Der vorhandene TypeScript-Daemon bleibt bis zur Gesamtparität die vollständige Referenz.

Die isolierte Gegenstelle benutzt ein Chromium-Canvas und einen künstlichen Oszillator, keine Kamera, kein Mikrofon und kein reales Gerät. Sie prüft das kopierte native Binary mit leerem PATH und einem expliziten FFmpeg-Pfad:

```powershell
$env:KVMHELM_TEST_BINARY = 'target/debug/kvmhelm.exe'
node scripts/native-jetkvm-interop.mjs
```

## MCP und stdio-Bridge

`mcp.rs`, `mcp_http.rs` und `mcp_bridge.rs` integrieren die sechs bestehenden Tools mit `rmcp` 3.7.0 auf demselben Core wie REST und UI. Unterstützt wird der bisherige Sessionhandshake mit den fünf Referenzrevisionen `2024-10-07`, `2024-11-05`, `2025-03-26`, `2025-06-18` und `2025-11-25`. Die neue zustandslose Protokollgeneration 2026 wird nicht beworben. Nicht vorhandene Ressourcen-, Prompt-, Task- und Completionmethoden liefern Protokollfehler. Taskaugmentierung wird vor Toolausführung abgewiesen, entsprechend der bestehenden Deklaration `execution.taskSupport: forbidden`.

`native/src/mcp-contract.json` enthält die tatsächlichen Versions-, Server-, Capability-, Instruktions- und Toolmetadaten des ursprünglichen TypeScript-SDKs einschließlich der aus Zod erzeugten Ein-/Ausgabeschemata und Annotations. Ein zusätzlicher Vergleich prüft die gesamte Datei gegen eine frische Registrierung im Referenz-SDK. Eine bewusste Aktualisierung erfolgt nach dessen Build mit `node scripts/rust-compat-fixture.mjs mcp-contract native/src/mcp-contract.json`. Der native Build bindet die kleine Vertragsdatei ein und startet dafür kein Node. Toolausführung und Validierung bleiben vollständig nativ. Die Wiregrenze erhält die vom neueren Rust-SDK entfernte ältere `execution`-Angabe sowie den ursprünglichen DELETE-Status 200; die älteste Protokollrevision wird vor der internen Header-Whitelist des SDKs angepasst. Fehlerhafte Toolargumente bleiben MCP-Parameterfehler, betriebliche Corefehler bleiben strukturierte Toolergebnisse.

Pro Listener gelten maximal 128 MCP-Transportsessions und 32 je Token, jeweils einschließlich noch nicht abgeschlossener Initialisierungen. Jede erhält eine eigene `mcp:<UUID>`-Clientidentität und bleibt an den ausstellenden Token gebunden. Offene identische JSON-RPC-IDs können nicht den Router eines noch laufenden Auftrags ersetzen. DELETE, Tokenwiderruf/-ablauf, eine Stunde Inaktivität und Listenerstopp schließen Transport und zugehörige Core-Sessions samt Leases/Eingaben. Die Bereinigung prüft jede Sekunde; lange GET-Streams werden auch bei gestautem Empfänger beendet. Sie teilen die bestehenden globalen und tokenbezogenen Streambudgets.

MCP-POSTs behalten ihren Annahmeplatz bis zum vollständigen Toolergebnis. Endliche Antworten haben maximal 64 MiB und ein Sammelbudget von 40 Sekunden; danach wird der betreffende Transport geschlossen und ein Verbindungsfehler gemeldet. Ein verlorener Socket beendet den angenommenen Coreauftrag nicht. Die Annahme gewöhnlicher HTTP-Antworten bleibt auch an bereits an Hyper übergebene Ausgabebytes gebunden, bis diese freigegeben sind. Langsame Leser können damit keine unbegrenzte Folge abgeschlossener Bildantworten außerhalb des Requestbudgets anhäufen. MCP-DELETE und die bisherigen Stop-/Release-/Close-Pfade verwenden das gesonderte Sicherheitsbudget.

Die native stdio-Bridge spricht ausschließlich den bestehenden Daemon an:

```sh
target/release/kvmhelm mcp --transport stdio --url http://127.0.0.1:8765 --pat-file .kvmhelm/native-preview/secrets/cli.pat
```

Sie öffnet keinen Store/Core und startet keinen Daemon. Ihre stdio-Verbindung bleibt bestehen, während die HTTP-Verbindung ausgetauscht wird. Nur `tools/list` und `list_computers` dürfen nach einem wiederherstellbaren Verbindungsfehler einmal erneut gesendet werden. Eingabe, Control, Open/Close und Screenshot werden nie automatisch wiederholt; der Client erhält `MCP_CONNECTION_LOST` und die bestehenden Hinweise zu neuer Geräteliste, Session und Beobachtung. Alte Gerätesessions, Leases und Bildreferenzen werden nicht restauriert. Die neue Verbindung liest die geschützte PAT-Datei erneut; UTF-8 mit BOM wird wie bei JavaScript-Trim akzeptiert. Authfehler verwerfen die alte Verbindung und schlagen den aktuellen Aufruf fehl, sodass nach Korrektur der Datei ein neuer Aufruf neu verbinden kann. PAT, Bilder und Eingabetexte erscheinen nicht in Logs.

Der stdio-Transport begrenzt Eingaben auf 256 KiB pro Zeile und hält höchstens 16 ausstehende Requests bis zur tatsächlichen stdout-Ausgabe. Volle Ausgabe erzeugt Rückstau vor weiterer Annahme. Abgebrochene Teilzeilen behalten ihren Präfix und verlieren keinen Annahmeplatz. Ungültige optionale Objekte, etwa `arguments: null`, werden nicht als ausgelassene Argumente ausgeführt. Überlange Zeilen werden bis zum nächsten Zeilenende verworfen und mit einem Protokollfehler beantwortet; die folgende vollständige Nachricht bleibt lesbar. Einzelne Ausgaben sind auf 64 MiB begrenzt. stdout enthält ausschließlich JSON-RPC; EOF und geordneter Stopp räumen die vorgelagerte MCP-Session auf.

`scripts/native-mcp-interop.mjs` kopiert das Binary wie der Browsercheck in ein temporäres Verzeichnis, startet native Prozesse mit leerem PATH und verwendet den ursprünglichen TypeScript-MCP-Client als unabhängige Gegenstelle. Der Check prüft Metadaten/Bilder, gemeinsame Controlarbitrierung, zwei Daemonneustarts im selben stdio-Prozess, Offlinefehler, PAT-Wechsel und Sessionbereinigung. Eine lokale Proxygegenstelle lässt eine echte synthetische Eingabe vollständig ausführen und verwirft erst danach deren Antwort; der Check zählt exakt einen Versand und prüft die strukturierte Verbindungsverlustantwort. Keine realen Geräte werden angesprochen.

```powershell
$env:KVMHELM_TEST_BINARY = (Resolve-Path target/debug/kvmhelm.exe).Path
node scripts/native-mcp-interop.mjs
```

## Geräte-Netzwerktransport

`transport.rs` verwendet einen gepoolten HTTP/1.1-Client und denselben Rustls-Zertifikatsprüfer für HTTP und WebSocket. Jede DNS-Auflösung prüft alle Antworten vor dem Verbindungsversuch; eine gemischte LAN-/öffentliche Antwort wird vollständig abgewiesen. Literale öffentliche IPs werden bereits an der Konfigurationsgrenze abgewiesen. Ambient-Proxies und automatische Redirects sind deaktiviert; Transportpfade müssen innerhalb desselben konfigurierten Origins bleiben. Es gibt maximal vier gleichzeitig gehaltene HTTP-Antworten je Gerät, ein begrenztes Idle-Pooling und Fünf-Sekunden-Fristen für Verbindungsaufbau, Antwortheader, Bodylesen und einzelne Socketversandvorgänge. JSON-Antworten sind auf 1 MiB begrenzt. Ein Disconnect cancelt ausstehende HTTP-Leser und verwirft den Pool; spätere Verbindungen erhalten einen neuen Pool.

Ein SHA-256-Fingerprint wird auf dem tatsächlich verwendeten TLS-Socket vor dem HTTP-/WS-Handshake mit Credentials geprüft. Bei gepinnten Verbindungen sind TLS-Session-Resumption und Early Data deaktiviert, damit jeder neue Socket erneut das Zertifikat prüft. Ein Pin setzt auch bei zusätzlich aktiviertem Insecure-Modus die Fingerprintprüfung durch. Ohne Pin gelten CA-/Hostnameprüfung oder der ausdrücklich konfigurierte Insecure-Modus; TLS-Handshake-Signaturen werden in allen Modi geprüft. Standardmäßig werden gebündelte Mozilla-Roots verwendet, eine Gerätekonfiguration mit `tls.ca_ref` liefert stattdessen ihre eigenen CA-Zertifikate. Pins auf einer HTTP-Adresse und ungültige CA-/Pinformate werden vor Credentials abgewiesen. TLS-Fehler werden ohne Roh-URL oder Credentials als öffentliche Fehler klassifiziert.

Der KVMD-Socket verwendet höchstens 64 wartende Nachrichten und 64 KiB ausstehende HID-Bytes; Eingangsnachrichten und Einzelframes sind ebenfalls auf 64 KiB begrenzt. Vor dem tatsächlichen Versand wird die Controlberechtigung erneut geprüft. Ein Send-Ergebnis bedeutet `sent`, keine Gerätebestätigung. Keine HID-Nachricht wird nach Fehler/Reconnect automatisch erneut gesendet. Key-/Button-Zustände werden vor dem Press-Versuch erfasst; Freigaben werden auch nach einem fehlgeschlagenen oder abgebrochenen Press versucht. Unbestätigt gebliebene Releases werden nicht als Erfolg ausgegeben. Ein Ping läuft alle zehn Sekunden; ein fehlender Pong über mehr als 30 Sekunden schließt den Socket. Alte Socketcallbacks dürfen aktuelle Capabilities nicht überschreiben.

PiKVM-Snapshot-Warmup wiederholt ausschließlich HTTP 503 mit 100 ms Abstand bis zur Vier-Sekunden-Grenze; Authfehler werden sofort zurückgegeben. JPEG-/PNG-Metadaten werden außerhalb des Tokio-Reaktors unter Eingabe-/Pixel-/Allokationsgrenzen gelesen, ohne vollständige Pixeldaten zu dekodieren. Der inkrementelle MJPEG-Parser behält nur begrenzte unvollständige Daten und einen Suchoffset, verarbeitet aufgeteilte Marker und begrenzt den Puffer auf 12 MiB sowie den einzelnen Frame auf 8 MiB. Ein Stream muss innerhalb von fünf Sekunden einen vollständigen nächsten Frame liefern. Es werden keine Mediendateien geschrieben.

Comet bleibt ein expliziter Herstelleradapter. Wie der vorhandene TypeScript-Code verwendet er die GL-KVMD-Ereignisse, bewahrt `vendor`, `model` und `protocol` in den Extensions und übersetzt fehlende erforderliche Endpunkte in `UNSUPPORTED_FIRMWARE`; Authfehler bleiben Authfehler. Die Implementierung behauptet keine Unterstützung anderer Comet-Protokolle. Native Janus-/Audiofähigkeiten sind bei diesen Zwischenstandsadaptern ausdrücklich als noch zu integrieren markiert. Audio aus dem ursprünglichen Backend bleibt Bestandteil des offenen Gesamtports.

## Noch zu integrierende Laufzeitabhängigkeiten

Der native JetKVM-Videopfad behält FFmpeg ausdrücklich als eigenen Helfer. Deshalb ist eine Installation mit JetKVM-Video derzeit kein einziges vollständiges Binary. Programmsuche, Prozessbesitz, Pipes, Grenzen und Stop sind integriert; reproduzierbare Releasepakete einschließlich passender Codec-Builds und ihrer Lizenzdateien sind noch zu erstellen. Der native Core startet ohne Node; vorhandene Plugins benötigen für ihren Node-Fork-/IPC-Vertrag einen optionalen Node-Adapter mit erhaltenen `Buffer`-Payloads. Dieser Adapter darf keine zweite Implementierung von Core, Leases, Persistenz oder HTTP-Daemon enthalten. Opus-/Plugin-/Plattformpaketierung und die jeweiligen Laufzeitnachweise bleiben offen. TLS und SQLite sind im aktuellen nativen Windows-Build statisch eingebunden.

- Die 14 Netzwerk-/Protokollprüfungen verwenden ausschließlich lokale HTTP-/TLS-/WebSocket-Gegenstellen. Sie prüfen PiKVM und beide Comet-Identitäten, Live-Capabilities, HID-/Pixelmapping, Snapshotwarmup und Abbruch, JPEG/PNG/MJPEG-Grenzen und aufgeteilte Marker, Heartbeat und Reconnect, CA/Hostname/Insecure, korrekte/falsche/gewechselte Pins vor Credentials, gemischte und geänderte DNS-Antworten, Redirectablehnung, HTTP-/HID-Budgets sowie den nativen Core mit regulär registriertem PiKVM-Adapter. Die zusätzliche Zertifikatinspektion liefert den tatsächlichen SHA-256-Fingerprint, ohne eine HTTP-Anfrage zu senden. Dabei wurde eine zunächst falsche Klassifikation verschachtelter TLS-Zertifikatsfehler korrigiert. Dies sind Protokollnachweise, keine Hardwareabnahme.
- Die zwanzig HTTP-/MCP-/CLI-Prüfungen decken die sechs Tools einschließlich Bilder/Replay, echte TCP-Abbrüche während eines angenommenen Widerrufs, Tokenattenuierung, Konfigurations-/Präferenz-CAS, Bodygrenzen, Host/Origin/Cookie/CSRF, erschöpfte Medien-/Kontrollbudgets und weiterhin erreichbare Sicherheitsrouten ab. Außerdem geprüft: Readiness bei ausgefallenem Store, freigegebene MJPEG-Abonnenten, SSE-Neustart/Widerruf, gemeinsamer HTTP-/TLS-Core mit Secure-Cookie und verweigertem Klartext-LAN sowie explizite Fehler bei vorhandener Plugininventur. Zwei Prüfungen starten eine kopierte native CLI mit leerem PATH und prüfen private einmalige PAT-Ausgabe, verhindertes Überschreiben ohne zusätzliche Tokenausgabe sowie Remote-Doctor/-Tokenverwaltung ohne zweiten Core. Ein zunächst fehlender expliziter Rustls-Cryptoprovider wurde im nativen Client und in den HTTP-Testclients ergänzt.
- Die neun zusätzlich ausgeführten Vergleiche gegen das Original bestehen. Insbesondere sind bestehende Tokens und AES-GCM-Dateien in beide Richtungen, die beschriebene Core-Sequenz und die tatsächlichen DOM-HID-Ereignisfolgen geprüft.
- Die acht MCP-Prüfungen innerhalb der zwanzig HTTP-Tests prüfen außerdem alle fünf Referenzversionen, vollständige Toolmetadaten und Capabilities, Bilder, Client-/Tokentrennung, gleichzeitige Initialisierungsgrenzen, abgewiesene Handshakes ohne Reservierungsleck, Idle-/Widerruf-/DELETE-/Shutdown-Bereinigung und weiter erreichbares DELETE bei erschöpftem Kontrollfenster. Ein echter TCP-Abbruch während eines bereits angenommenen Wait-/Klick-Batches erhält die Ausführung; eine gleichzeitig wiederverwendete JSON-RPC-ID wird abgewiesen, ein identischer Core-Retry sendet nicht erneut. Fehlerhafte Argumente und nicht unterstützte MCP-Methoden/Taskaugmentierung werden vor Ausführung abgewiesen. Die Integration fand und korrigierte zunächst verlorene ältere `execution`-Metadaten und den abweichenden SDK-DELETE-Status; eine numerisch gleichwertige Annotationsdarstellung `1.0` wird im Rust-Test als Zahl verglichen.
- Fünf weitere Transportprüfungen decken blockiertes stdout, Rückstau bis zur tatsächlichen Ausgabe, abgebrochene Teilzeilen, fehlerhafte/übergroße stdio-Nachrichten samt folgender gültiger Nachricht, Lebenszeit bereits gepufferter HTTP-Ausgabebytes sowie IPv6-/56-/IPv4-mapped-Rategrouping ab. Die beiden neuen Originalvergleiche prüfen die vollständigen MCP-Vertragsdaten und die tatsächliche `express-rate-limit`-Schlüsselbildung.
- Der unabhängige MCP-Check besteht mit nativer stdio-Bridge sowohl gegen den nativen als auch gegen den unveränderten TypeScript-Daemon. Geprüft sind Metadaten/Bilder/Control, exakt ein Versand bei nach Ausführung verlorener Eingabeantwort, zwei Neustarts und zeitweise Nichterreichbarkeit im selben stdio-Prozess, erneutes Lesen einer gewechselten UTF-8-BOM-PAT-Datei nach Widerruf sowie Freigabe einer noch offenen Gerätesession beim stdio-EOF. Eine vor Versand abgewiesene HTTP-429-Anfrage behält die gültige Controlsession und wird nicht mit einem ungewissen Verbindungsverlust gleichgesetzt. Die zusätzlichen Prüfungen sind in der CI-Matrix eingetragen; externe CI wurde hier nicht ausgeführt.
- Das native Debugbinary mit eingebetteten Assets ist gebaut. `scripts/ui-layout.mjs` besteht gegen das kopierte Binary mit leerem PATH und gegen den unveränderten TypeScript-Daemon: leere Installation, drei Simulatorbilder, gespeicherte Reihenfolge, Dark/Light, kompakte Darstellung, Anmeldung nach Browser-/Daemonneustart ohne Cookies und Logout. Der erste native Browserlauf fand die zuvor nach UUID sortierte Geräteliste; Core und Tokenlisten verwenden jetzt die ursprüngliche Einfügereihenfolge. Der gezielte Coretest prüft bewusst umgekehrt sortierte UUIDs.

- Die sieben zusätzlichen JetKVM-Bausteinprüfungen decken Fragment-/Parameter-/Sequenzgrenzen, unvollständige/übergroße Einheiten, einen fehlenden Decoder, öffentliche SDP-/Trickle-Kandidaten vor RTC-Mutation, Controlwiderruf an der tatsächlichen Versandgrenze, weiter belegte Annahmeplätze nach Aufruferabbruch sowie nullable RPC-Fehler, numerische IDs und asynchrone Ereignisse ab. Der neunte Originalvergleich prüft die H.264-Ausgabe bei Sequenzüberlauf, Duplikaten, Verlust, STAP-A, FU-A und gecachten Parametern gegen die tatsächliche TypeScript-Assemblerklasse. Bei fehlenden Markern und widersprüchlichen FU-Fragmenten ist der native Pfad bewusst konservativer und verlangt einen neuen Keyframe.
- Der JetKVM-Chromiumcheck prüft echtes WebRTC-H.264/JPEG und vom Browser tatsächlich empfangene RTCP-PLI-Keyframe-Anfragen, die exakte Folge der USB-Reports aus der ursprünglichen DE-/AltGr-/Tottasten-/Mausplanung, sechs gleichzeitige Tasten, gesamte Batch-Vorprüfung, RPC-Antwortverlust ohne erneuten Tastendruck beim Retry, Cookie-Wiederverwendung, Live-Signal/USB, MJPEG-Ende und übernommene Fremdsessions mit widerrufener Controllease. Falsches Passwort, nicht abgeschlossenes Setup und öffentliche ICE-Kandidaten werden abgewiesen. Er läuft auf ENVY zusätzlich mit `KVMHELM_TEST_ICE_LAN=1`: beide Seiten entfernen Loopback-Kandidaten und der Browser prüft die tatsächlich gewählte LAN-Gegenstelle. Damit sind lokale Mehrschnittstellenfälle geprüft; die zusätzliche Variante verlangt eine nutzbare lokale LAN-IPv4-Schnittstelle. Ein früher Fehler bei unbrauchbaren ICE-Paaren wurde korrigiert: UDP-/ICMP-Fehler einzelner Kandidaten beenden nicht mehr die gesamte ICE-Suche. Der Wirecheck enthält auch erfolgreiche Antworten mit `error: null`. Das native Binary wird jeweils in ein temporäres Verzeichnis kopiert und mit leerem PATH gestartet; FFmpeg ist ausdrücklich als Helferpfad angegeben. Die CI enthält die portable Loopbackvariante; externe CI wurde hier nicht gestartet.

Linux/macOS, physische PiKVM-/JetKVM-/Comet-Geräte sowie die Audio-/Plugin-Gesamtpfade wurden noch nicht ausgeführt. JetKVM-HID/Video ist ausschließlich gegen lokale synthetische Gegenstellen geprüft. Ein natives Laufzeitprofil für Idle, aktive Geräte, Videowand, Audio und langsame Consumer existiert noch nicht; aus den bisherigen Builds und Funktionsprüfungen werden keine RAM-/CPU-/Latenzverbesserungen abgeleitet.

Als nächster Integrationsschritt folgt der gemeinsame native Audiopfad: Janus/Opus und JetKVM-Zielaudio, PCM-Verteilung und vorhandene WebSocket-/UI-Lebenszyklen. Danach bleiben Plugin-IPC, die vollständige API-/UI-Abnahme, Paketierung und gemeinsame Laufzeitmessungen erforderlich. Die bestehende TypeScript-Implementierung wird erst entfernt, wenn ihre Funktionen im nativen Gesamtpfad nachgewiesen sind.
